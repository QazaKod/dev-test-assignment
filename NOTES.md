### Если запускать сервис в нескольких экземплярах с общей БД (PostgreSQL)
- **Идемпотентность:** добавить уникальный индекс (`UNIQUE`) на поле `order_id` в таблице назначений. Если два запроса на один заказ придут на разные сервера, второй запрос не создаст дубль.
- **Защита от превышения лимитов (гонки):** сейчас всё хранится в памяти одного процесса. С несколькими серверами нужно выполнять проверку лимита и назначение в одной транзакции с блокировкой строки (например, `SELECT ... FOR UPDATE` по филиалу на выбранную дату). Это гарантирует, что два сервера параллельно не превысят `dailyLimit`

### Если будет несколько экземпляров сервиса и PostgreSQL
- Текущая очередь в памяти (`withMasterLock`) защищает только один процесс Node.js — при нескольких серверах она не сработает, поэтому блокировку нужно перенести в PostgreSQL.
- **Лучшее решение на уровне БД — Exclusion Constraint (с расширением `btree_gist`):**  
  Создать ограничение на таблице бронирований, запрещающее пересечение диапазонов `tstzrange("start", "end")` для одного `master_id` при условии `WHERE status = 'active'`. Тогда при параллельной вставке с разных серверов БД гарантированно пропустит только первый `INSERT`, а второй завершится ошибкой конфликта, которую сервер превратит в `409 slot_unavailable`.
- **Альтернатива:** выполнять проверку слота и `INSERT` в одной транзакции, предварительно блокируя мастера через `SELECT ... FOR UPDATE` по строке мастера (или `pg_advisory_xact_lock`)..
